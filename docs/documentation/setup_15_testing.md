# Setup 15 — Testing

## Objetivo

No arranca RSpec desde cero (ya se usa desde Setup 6) — cierra la fase decidiendo qué hacer con cada pending acumulado, centraliza lo que se venía repitiendo entre specs, y deja por escrito el criterio de "qué probar y qué no" para que el próximo módulo no tenga que redescubrirlo.

## Decisiones arquitectónicas

* **Los pending sin lógica real que probar se borran, no quedan pending para siempre**: `IconsHelper`/`BreadcrumbsHelper`/`PagesHelper`/`RolesHelper`/`UsersHelper`/`DashboardHelper` son o bien módulos vacíos (los tres últimos, generados por scaffold, nunca les agregaste métodos — vos preferiste `charts_helper.rb`/`audit_logs_helper.rb` como archivos propios) o helpers cuya única lógica es un lookup estático ya inventariado a ojo en `/styleguide`. Un pending eterno es peor que nada: parece "falta hacer" cuando en realidad es "no hay nada que hacer acá".
* **El criterio real para decidir si un helper merece spec**: ¿tiene lógica de decisión (branches, mapeos, formato) que pueda estar mal sin que se note a simple vista? `AuditLogsHelper#audit_action_badge` sí (un mapeo mal hecho — "destroy" con badge-success — no se nota de inmediato). `IconsHelper#icon` no (es un lookup exhaustivo, ya lo ves entero en el styleguide).
* **`RolePermission` sin spec dedicado**: mismo criterio que `Session` desde Setup 7 — un modelo de join puro se prueba indirectamente a través de los modelos que lo usan (`role.permissions <<` ya se ejercita en `role_spec.rb`/`role_policy_spec.rb`).
* **View specs (`dashboard/index.html.tailwindcss_spec.rb`, `roles/index.html.tailwindcss_spec.rb`) se borran**: ya tenés request specs reales para las dos rutas — un view spec aislado necesita el mismo stubbing que un request spec pero prueba algo menos realista (markup renderizado sin pasar por el controller/policy de verdad). Preferimos request specs.
* **`AdminFormBuilder` se prueba indirectamente, no en aislamiento**: instanciar `ActionView::Base` a mano para testear un form builder es frágil entre versiones de Rails, como ya quedó anotado en Setup 9. La cobertura real ya existe: `sessions_spec.rb`, `passwords_spec.rb`, `users_spec.rb` renderizan formularios reales construidos con el builder. Se borra el pending, se documenta la decisión en vez de dejarla implícita.
* **`spec/support/` recién ahora se activa**: `rails_helper.rb` traía la línea de autoload comentada desde que Rails lo generó (default del template) — nadie la había necesitado hasta que empezaron a aparecer `sign_in` reinventado en cada request spec.
* **Faker donde el valor específico no importa**: ya estaba en el Gemfile (agregado junto con `rspec-rails`/`factory_bot_rails`) pero nunca se usó. Factories que ya pasan overrides explícitos cuando el valor importa (`create(:role, name: "Editor", key: "editor")`) no cambian de comportamiento.
* **SimpleCov solo para visibilidad, sin threshold que rompa el build**: forzar un mínimo de cobertura ahora sería prematuro sin saber dónde está parado el número real. Si Setup 16 (CI/CD) quiere hacerlo gate del pipeline, es una decisión de esa fase con datos reales.

## Alternativas consideradas

* **Dejar los pending como están** → descartado: son ruido en cada corrida de `rspec` (11 líneas de "Pending" que hay que leer y descartar mentalmente cada vez).
* **Escribir specs de todos modos para los helpers vacíos** ("por las dudas") → descartado: un test que solo verifica que un método existe y devuelve un string no detecta ningún bug real, solo agrega mantenimiento.
* **`rails-controller-testing`/specs de controller clásicos** → no evaluado: el proyecto ya está 100% en request specs, no hay razón para introducir un estilo distinto a esta altura.

```ruby
require "rails_helper"

RSpec.describe Permission, type: :model do
  it "es válido con una key en formato recurso.acción" do
    expect(build(:permission, key: "users.manage")).to be_valid
  end

  it "normaliza la key a minúsculas" do
    permission = create(:permission, key: "Users.Manage")
    expect(permission.key).to eq("users.manage")
  end

  it "requiere el formato recurso.acción" do
    expect(build(:permission, key: "invalido")).not_to be_valid
    expect(build(:permission, key: "con espacios.no")).not_to be_valid
  end

  it "no permite claves duplicadas" do
    create(:permission, key: "users.manage")
    expect(build(:permission, key: "users.manage")).not_to be_valid
  end
end
```

**docs/conventions/testing.md** (nuevo):

```markdown
# Convenciones de testing — admin-gem

## Qué sí se prueba
- Autorización y autoprotección (`spec/policies/`) — es donde un bug es
  silencioso y grave (nadie nota que le faltó un `authorize`).
- Comportamiento de seguridad cross-cutting: sesión cortada al desactivar un
  usuario, mensajes de login que no distinguen cuenta inexistente de
  desactivada, diffs de auditoría que nunca exponen `password_digest`.
- Validaciones y normalización de modelos con lógica real (formato, unicidad,
  scopes de filtro).
- El camino feliz + el camino denegado de cada request protegido por Pundit.

## Qué no se prueba (a propósito, no por omisión)
- Helpers que son un lookup estático sin lógica de decisión (`IconsHelper`).
  Se verifican a ojo en `/styleguide`, que ya los inventaria a todos.
- `AdminFormBuilder` en aislamiento — se prueba indirecto, a través de los
  request specs de cualquier vista que use un formulario real.
- Modelos de join puro (`RolePermission`, `Session`) — se ejercitan a través
  del modelo que los usa (`role.permissions <<`, `user.sessions`).
- View specs aislados — si ya existe un request spec para esa ruta, no se
  duplica con un view spec del mismo template.

## Regla para decidir si un pending se completa o se borra
Un pending generado por scaffold se borra si no hay lógica de decisión que
probar (branches, mapeos, formato). Se completa si la hay. Nunca queda
pending "por las dudas" — o se prueba, o se borra con esta lógica documentada.

## Autenticación en request specs
`sign_in(user)` (en `spec/support/authentication_helpers.rb`, incluido
automáticamente en specs `type: :request`) — no reinventar esto por archivo.

## Factories
Faker para datos donde el valor específico no importa (`Faker::Internet.email`).
Cuando el valor sí importa para el test (un permiso puntual, un rol con nombre
específico), se sigue pasando explícito: `create(:role, name: "Editor", key: "editor")`.
```

## Verificación de consistencia

Nada de esto cambia comportamiento de la app — solo la suite de tests y qué tan honesta es sobre lo que cubre. `password` seguía siendo legible desde el objeto `user` recién creado en memoria (así es como `has_secure_password` funciona: el setter guarda el valor en texto plano en una variable de instancia que vive mientras el objeto Ruby exista) — por eso `sign_in(user)` centralizado sigue funcionando igual que los usos sueltos que reemplaza.

## Seguridad

Nada nuevo — esta fase es sobre el proceso de testing, no sobre superficie de ataque. El único cambio con implicancia de seguridad es indirecto: con `spec/support` activo y `sign_in` centralizado, cualquier cambio futuro al flujo de login (ej. 2FA) se actualiza en un solo lugar en vez de en cada spec que lo reinventó por su cuenta.

## Mantenibilidad y compatibilidad futura

`docs/conventions/testing.md` es lo que el próximo módulo (o quien clone el boilerplate) lee antes de preguntarse "¿esto necesita un spec?" — la respuesta ya está escrita, con el razonamiento, no solo la regla.
